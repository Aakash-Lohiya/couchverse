# Latency, drift and failure-handling measurements

Raw numbers: [`latency-results.json`](latency-results.json) (regenerated by `npm run loadtest`).

## Test conditions

| | |
| --- | --- |
| date | 2026-10-15 |
| machine | Windows 11, Node v24.20.0, server and all clients on one host |
| network | loopback (`localhost`), WebSocket transport, `perMessageDeflate` off |
| room | 12 concurrent members, then 2 late joiners (14 total) |
| controls | 40 host controls, one every 1.2 s, cycling seek-random → pause → play → seek +30 s, plus 12 controls in the concurrency phase |
| players | `VirtualPlayer` from `shared/sync-engine.js`: each client has a random clock-rate error of ±1.5 % and is driven by the real `SyncController`; every 3rd control a random viewer is stalled for 300-900 ms |
| harness | `scripts/loadtest.js` (socket.io-client, real server, real protocol) |

### How each metric is measured

- **Control propagation** = `viewer.serverNow()` at apply − `originTs` stamped by the host when it emitted the control (both in server time via NTP-style offsets; see ARCHITECTURE.md). This is host → server → viewer → applied, measured independently on every viewer for every control.
- **Host emit → server ack** = round trip for the control's acknowledgement callback.
- **Steady-state drift** = |player time − expected| sampled every 100 ms on every viewer while playing, excluding a 1 s window after each control and 2.2 s after each injected stall (so it measures how tightly peers track the timeline, not the correction itself).
- **Stall recovery** = time from the end of an injected stall until |drift| < 500 ms again.
- **Late join → in sync** = time from `room:join` emit until the joiner's |drift| < 500 ms.
- **Reconnect → in sync** = a viewer's transport is closed with `socket.io.engine.close()`; time until it has reconnected, rejoined and has |drift| < 500 ms.
- **Burst convergence** = host transferred to another member who immediately fires 10 seeks while the old host also seeks; after 1.5 s every client must hold the same state version and the same expected position.

Steady-state drift is dominated by the controller's dead-band: with a 120 ms soft threshold and a ±6 % rate nudge, a player with 1.5 % clock error oscillates in a ~±150 ms band. Tightening `SYNC.SOFT_DRIFT_S` trades that for more frequent (still inaudible) rate changes.

### Browser measurements (manual, two Chromium tabs, loopback)

Two real users (host on `localhost`, viewer on `127.0.0.1`, same machine) watching the local Sintel clip, read from the in-app stats badge and by sampling `video.currentTime` in both tabs within 10 ms of each other:

| scenario | observed |
| --- | --- |
| viewer joins 30 s into playback | lands within 110 ms of the host |
| host seek via seek bar | both tabs land on the identical frame (`1.842027` s in both) |
| host transfer, new host plays | old host follows; positions within 450 ms at the first sample, pulled inside the dead-band by the rate nudge within seconds |
| socket ping (RTT) | 1-2 ms; clock offset ±1 ms |

### What a real LAN changes

On Wi-Fi the clock offset error and propagation rise with RTT (typically 2-20 ms). The engine's budget: propagation ≤ 250 ms needs RTT/2 + server processing (≈ 0.2 ms per broadcast fan-out) ≤ 250 ms, which holds up to RTTs of several hundred ms. Drift after correction depends only on the clock agreement (lowest-RTT-of-8 sampling keeps error well under 50 ms on any LAN) and on how fast the player seeks (hard seeks lead by 150 ms to cover typical seek latency).

## Failure handling

| failure | behaviour | verified by |
| --- | --- | --- |
| viewer's player stalls / buffers | drift grows → rate nudge → hard seek above 900 ms (1.2 s cooldown); with *Hold for buffering* on, the host pauses the whole room instead and resumes together | load test (13 injected stalls, worst recovery 459 ms), unit test |
| viewer's socket drops | socket.io reconnects with backoff, client re-emits `room:join`, receives a snapshot and lands on the timeline; member record kept 30 s so presence survives a blip | load test (208 ms to resync) |
| host's socket drops | after 12 s the longest-present member is auto-promoted; chat shows "X is now host (previous host left)" | room manager sweep |
| host leaves explicitly | immediate auto-transfer | `leave(hard)` |
| two tabs for one user | the newer tab supersedes the older one, which shows "opened elsewhere" | server `join()` |
| stale / concurrent controls | version-tagged; stale play/pause toggles dropped, seeks win, non-host controls rejected | load test burst phase (1 version, 0.001 s spread) |
| browser blocks autoplay | "Tap to join playback" overlay; engine resumes on gesture | `onCorrection('autoplay-blocked')` |
| media URL blocked by CORS / host | player retries once through the server relay (`/api/media/proxy`, Range pass-through) | manual (Google sample bucket returning 403) |
| server restart | rooms rehydrated from SQLite (identity, media, queue, timeline, settings, polls); clients rejoin on reconnect | manual |
| wrong passcode / unknown room | explicit error, passcode prompt | manual |
| empty room | deleted after 10 min idle | sweep |

## Reproduce

```bash
npm run dev                              # terminal 1
npm run loadtest -- --users 12 --controls 40 --interval 1200   # terminal 2
```

Exit code 0 means all four pass criteria held (≥ 10 users, propagation p95 ≤ 250 ms, drift p95 ≤ 500 ms, burst convergence). To test across machines, run the server on one host and pass `--server http://<host>:4000` from another.
